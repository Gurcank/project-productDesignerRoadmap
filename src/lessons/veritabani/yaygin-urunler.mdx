Ürün adlarını duyduğunda kategorisini bilmen yeterli. Ürün seçimi tasarımı doğrudan etkilemez; etkilediği yer, o veritabanının **ne garanti ettiğidir.**

## Beş ürün

| Ürün | Tür | Ne zaman |
|---|---|---|
| **PostgreSQL** | İlişkisel | Modern varsayılan. Güçlü, açık kaynak, JSON desteği var, eklentilerle genişler. Emin değilsen bu |
| **MySQL** | İlişkisel | Çok yaygın ve olgun. WordPress ve klasik web yığınlarında baskın |
| **SQLite** | İlişkisel (dosya tabanlı) | Tek dosyada çalışır, sunucu gerektirmez. Küçük projeler, mobil uygulamalar, yerel geliştirme |
| **MongoDB** | Belge | Esnek yapılı veri; en yaygın belge veritabanı |
| **Redis** | Anahtar-değer | Önbellek, oturum, kuyruk, sayaç. Ana veritabanı olarak değil, yanında |

**Tasarım için sonuç:** ilişkisel bir veritabanı, arayüzde "bu iki kayıt tutarlı olmalı" varsayımını güvenilir kılar; belge veritabanı bunu garanti etmez.

<Case>

Demlik'in dünyasında beş ürünün dördü var:

1. **PostgreSQL:** ana veritabanı; müşteriler, dükkânlar, siparişler, iadeler.
2. **Redis:** oturumlar, giriş denemesi sayaçları, menü önbelleği.
3. **SQLite:** mobil uygulama son siparişlerin bir kopyasını cihazda tutuyor; bağlantı yokken "Son siparişini tekrarla" düğmesi neyi tekrarlayacağını gösterebiliyor.
4. **MySQL:** Demlik'in değil; bazı dükkânların WordPress sitelerinin altında.

MongoDB konuşulmadı; ürün özelliklerinin esnekliği PostgreSQL'in JSON alanıyla karşılandı.

</Case>
